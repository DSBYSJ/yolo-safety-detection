# 架构设计

> 本文是**面向开发者**的架构说明：讲清楚「系统由哪些模块组成、数据怎么流动、
> 哪些设计决策是刻意的、往哪个方向扩展」，帮助新开发者快速上手与安全改动。
> 面向使用者的操作说明见 [README](../README.md)。

## 一、系统概览

```
┌───────────────────────────── Web 浏览器（电脑 / 手机）────────────────────────────┐
│  11 个页面（Jinja2 模板 + ECharts）   ·  MJPEG 流   ·  base64 逐帧 POST             │
└────────────────────────────────────────┬────────────────────────────────────────────┘
                                          │ HTTP / HTTPS（cheroot WSGI 服务器）
┌────────────────────────────────────────┴────────────────────────────────────────────┐
│                                     Flask 应用层（webapp/app.py）                    │
│  路由注册 / 参数校验 / 权限与异常兜底 / 部署状态记录 / 摄像头配置管理                   │
└──────┬──────────────┬──────────────┬──────────────┬──────────────┬───────────────────┘
       │              │              │              │              │
┌──────┴─────┐ ┌──────┴─────┐ ┌─────┴──────┐ ┌─────┴──────┐ ┌─────┴──────────┐
│ 检测推理    │ │ 摄像头链路  │ │ 人脸能力    │ │ 训练/评估   │ │ 记录 / 统计     │
│ detector    │ │ camera     │ │ face_db    │ │ train_mgr  │ │ db             │
│ video_jobs │ │ camera_db  │ │ equip      │ │ (train.py  │ │ (SQLite records)│
│            │ │            │ │ phone_face │ │  val.py)   │ │                │
│            │ │            │ │ attendance │ │            │ │                │
│            │ │            │ │ panel_ck   │ │            │ │                │
└──────┬─────┘ └──────┬─────┘ └─────┬──────┘ └─────┬──────┘ └─────┬──────────┘
       │              │              │              │              │
┌──────┴─────────────────────────────┴──────────────┴──────────────┴─────┐
│ 基础设施：YOLOv8（GPU）· InsightFace buffalo_l（CPU）· OpenCV · SQLite · 中文字体 │
└─────────────────────────────────────────────────────────────────────────────┘
```

技术栈：**Ultralytics YOLOv8**（目标检测，GPU）· **Flask + cheroot**（Web / WSGI 服务器）·
**OpenCV**（图像 / 视频 / 摄像头）· **InsightFace**（人脸识别，CPU）· **SQLite**（持久化）·
**ECharts**（可视化）· **psutil**（训练进程控制）。

## 二、模块职责

### webapp/ 应用主体

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| `app.py` | 路由与接口入口；启动时初始化各库并 `seed_from_env()` | 手机端等逐帧接口必须「快速失败」而非排队 |
| `config.py` | 全局配置：模型清单 `MODELS`、路径、摄像头、环境变量解析 | 新加检测任务只需改这里，前端自动生效 |
| `detector.py` | YOLO 推理封装、中文标签绘制、推理串行锁、权重路径解析 | 所有推理必须过 `_infer_lock` |
| `camera.py` | 单例抓帧线程 + MJPEG 流 + 周期性落库 + 摄像头切换 | 源解析优先级：页面配置 > `CAMERA_SOURCE` > `CAMERA_INDEX` |
| `camera_db.py` | 多路摄像头配置：增删改查、地址校验、凭据脱敏 | 列表接口绝不返回明文密码 |
| `face_db.py` | 人脸底库：特征提取、比对、临时编号、按人统计 | 只走 CPU；模型缺失时明确报错、绝不联网下载 |
| `equip.py` | 装备按人归属：安全帽/口罩框按空间重叠配到人脸 | 三态语义 `1/0/NULL`，不能把「无信息」当「未戴」 |
| `attendance.py` | 人脸打卡：按日/区间核算打卡与缺勤 | 与 Flask 解耦，可单测；`is_temp = 0` 恒成立 |
| `panel_checkin.py` | 面板打卡：页面内独立刷脸打卡 | 只写自己的表；绝不调用 `face_db.add_seen` |
| `phone_face.py` | 手机端人脸识别：模式判定、节流、结果整理 | 按客户端 id 节流，互不顶替 |
| `video_jobs.py` | 视频后台检测任务（独立线程 + H.264 转码） | 异步 job_id 轮询进度 |
| `train_manager.py` | 在线训练/评估子进程管理：启动、暂停/继续/停止、指标读取 | 训练与评估互斥（抢显存） |
| `db.py` | 检测记录（SQLite 薄封装，WAL 模式） | 线程局部连接 |
| `imageio_cn.py` | 中文路径安全的图像读写 | 替代 `cv2.imread/imwrite` |
| `fontutil.py` | 跨平台中文字体加载 | Windows→macOS→Linux 探测 |

### 刻意「与 Flask 解耦」的模块

`attendance.py`、`panel_checkin.py`、`phone_face.py`、`equip.py`、`camera_db.py`、
`train_manager.py` 等**不 import Flask**，纯函数 + SQLite + numpy。
这样做的目的：

1. 可以脱离 Web 服务直接跑单元测试（CI 里无需起服务）；
2. 逻辑集中、便于代码审查（核心口径一眼看完）；
3. 未来若拆成独立服务 / CLI 工具，逻辑层可直接复用。

## 三、数据流

### 3.1 在线检测（图片）

```
浏览器上传图片 → app.py 校验格式/kinds/conf → imageio_cn.imread
  → detector.infer_image(加锁, 逐个 kind 推理) → detections + counts
  → 结果图 imageio_cn.imwrite → 落库 db.insert_record → 返回 json
```

### 3.2 摄像头实时监控

```
camera.py 单例线程：VideoCapture → 逐帧 YOLO 推理(加锁) → 画框/人脸识别
  → 编码 JPEG → 存入 _state（MJPEG 生成器持续吐帧给浏览器）
  → 有目标且距上次落库 ≥5s → 写一条 records
```

### 3.3 手机端逐帧检测

```
手机 getUserMedia → 压 JPEG → base64 POST /api/phone/detect
  → 解码 → infer_image(timeout=2)（等不到锁返回 503 + skip，宁可丢帧不可排队）
  → 按 face_mode 节流跑人脸 → equip.summarize 按人归并
  → 返回 counts + detections + faces（预览不落库）
  → 仅 save=1 时落盘 + 落库 + 写 face_seen
```

### 3.4 训练 / 评估

```
/train 页 → POST /api/train/start → train_manager.start 启动子进程
  → 子进程跑 train/train.py → 产物写 runs/<kind>_<size>/
  → 页面每 4s 轮询 /api/train/status（读 results.csv + 日志尾部）
  → 暂停/继续：psutil 挂起/恢复整棵进程树；停止：terminate 并释放显存
  → 训练完成 → 部署为线上权重 models/<kind>.pt + 写 .deployed.json
```

### 3.5 人脸流水 → 考勤

```
识别到人脸 → face_seen 流水（person_id / is_temp / 装备三态 / source）
  → attendance.daily_status(day)：应到名单(底库) − 当日有记录的人 = 缺勤
  → 趋势 / 区间台账聚合
```

## 四、数据库设计

所有库都在 `webapp/data.db`（SQLite，WAL 模式，启动时自动建表；`init_db()` 幂等）。

### 4.1 `records` —— 检测记录

| 字段 | 说明 |
| --- | --- |
| `id / created_at` | 主键 / 时间 |
| `source_type` | `image` / `video` / `camera` |
| `source_name` | 文件名或来源描述 |
| `kinds` | 检测任务组合，如 `helmet` / `helmet+mask` |
| `helmet / head / mask / face` | 四类计数（违规类为 head / face） |
| `num_objects / avg_conf / duration_ms` | 目标数 / 平均置信度 / 推理耗时 |
| `image_path / video_path` | 结果产物（static 下相对路径） |
| `details` | JSON 目标明细 |

### 4.2 `face_persons` + `face_seen` —— 人脸底库与识别流水

- `face_persons`：注册人员，含 L2 归一化后的 512 维 `embedding`（BLOB）与缩略图；
- `face_seen`：每次识别记录，含 `person_id / person_name / is_temp / score`；
  通过幂等的 `ALTER TABLE` 增量升级出 **`hat_state` / `mask_state`（三态）** 与 `source`。

> **三态语义**（本项目最关键的口径）：`1`=佩戴、`0`=确实未戴、`NULL`=本帧无该类装备框。
> 摄像头没对准、模型漏检都会导致无装备框，若一律记 `0` 会把员工大面积误判成违规，
> 因此「无信息」必须与「未戴」区分（详见 README 7.2）。

### 4.3 `cameras` —— 多路摄像头配置

含 `name / type(rtsp|http|device) / url(可能含明文凭据) / location / note /
enabled / last_ok_at / last_error`。列表接口一律脱敏返回；只有建连时才取原文。

### 4.4 `panel_checkin_events` —— 面板打卡（独立）

含 `person_id / person_name / score / checkin_at / day`。
**刻意与 `face_seen` / `records` 隔离**（表名带 `panel_` 前缀），
避免污染出勤统计与合规统计（详见 README 7.5）。

## 五、关键设计决策

| 决策 | 位置 | 为什么 |
| --- | --- | --- |
| 推理全局串行锁 `_infer_lock` | `detector.py` | YOLO 模型对象非线程安全，多线程并发 `predict()` 会在 CUDA 上下文互相踩踏直至死锁 |
| 默认 cheroot 而非 Flask dev server | `app.py` | Flask dev server 在 HTTPS 下不回收断开连接，`CLOSE_WAIT` 堆积会把整站打死；cheroot 原生 SSL + 连接可回收 |
| 手机端接口快速失败（`timeout=2` → 503 + skip） | `app.py` | 逐帧接口宁肯丢帧也不排队，队列堆积会让页面整体卡死 |
| 装备归属三态 `1/0/NULL` | `face_db.py` / `equip.py` | 「没拍到」≠「没戴」，统计违规率分母只算有信息次数 |
| 面板打卡独立表 + 只读 `face_db` | `panel_checkin.py` | 不写 `face_seen` 就不污染任何现有报表，靠表名前缀一眼可辨 |
| 权重回退链 `models/<kind>.pt` → `runs/<kind>*/best.pt` | `detector.model_path()` | 只删部署权重不会让检测「彻底不可用」，行为可预期 |
| 摄像头源解析优先级 | `camera.py` | 页面配置 > 环境变量网络流 > 设备索引，旧部署行为不变 |
| 人脸识别只走 CPU + 按间隔节流 | `face_db.py` / `camera.py` | 不与 YOLO 抢显存；人脸 200–400ms/帧，逐帧会把画面拖成幻灯片 |
| 图像读写走 `imageio_cn` | `webapp/imageio_cn.py` | `cv2.imread/imwrite` 在中文路径下静默失败，裂图而接口仍报成功 |
| 人脸模型缺失时明确报错、绝不联网下载 | `face_db.py` | 国内直连 GitHub/HF 超时，宁可告诉用户怎么放模型，也别卡在永远不返回的请求上 |
| 训练用 psutil 挂起进程树 | `train_manager.py` | 训练进程会派生子进程做数据加载，暂停要整棵树一起挂起才干净 |
| 主题 / 侧边栏状态存 `localStorage` | `base.html` | 手动选择优先于系统偏好；分组收起状态重载后还原 |

## 六、扩展点

### 6.1 新增一个检测任务（如「反光背心」）

1. `webapp/config.py` 的 `MODELS` 加一项 `{title, file, names, names_cn}`；
2. `datasets/` 加构建脚本产出 `data.yaml`（类别 id 与 `names` 一致）；
3. 前端导航/检测页/训练页的 kind 下拉 **自动生效**（`MODELS` 注入所有模板）；
4. 若该任务含新违规类别，把英文名加进 `config.BAD_CLASSES`；
5. 在 `datasets/*/data.yaml` 与 `config.MODELS` 一致的前提下，单元测试
   `TestConfig.test_model_names_match_data_yaml` 会帮你校验类别没写错。

### 6.2 新增一类摄像头来源

在 `camera_db.py` 的 `SOURCE_TYPES` / `TYPE_CN` 里加类型，并在
`resolve_url()` 中给出「类型 → 取流值」的转换分支即可；页面下拉会自动出现该项。

### 6.3 新增一个页面

1. `webapp/templates/` 新建模板并 `{% extends "base.html" %}`；
2. `app.py` 加路由，并在 `base.html` 的 `NAV_GROUPS` 里登记（选择所属分组）；
3. `tests/regression.py` 的 `test_pages` 页面列表与 CI 冒烟测试路径列表加上新路由。

### 6.4 接入外部考勤 / OA 系统

数据出口建议统一走 `att_daily` 日结（见 `docs/考勤系统接入设计方案.md`），
而不是原始 `face_seen` 流水。

## 七、测试策略

- **单元测试** `tests/test_unit.py`（187 项）：不依赖服务 / GPU / 数据集，
  覆盖各业务模块的纯逻辑；核心口径（面板打卡独立性、装备三态、考勤日期边界）
  都有专门用例钉死；
- **回归测试** `tests/regression.py`：需服务运行中，端到端覆盖页面可达性、
  检测、落库、评估达标断言等；
- **CI** `.github/workflows/ci.yml`：双 Python 版本下语法检查 → 模块导入 →
  单元测试 → 服务冒烟。
