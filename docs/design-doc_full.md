# 基于 YOLOv8 的安全帽/口罩佩戴检测系统设计与实现

**YOLOv8 安全帽/口罩佩戴检测系统 设计说明书**

---

## 摘要

在建筑施工、生产车间、矿区等作业场景中，安全帽与口罩是保障作业人员生命安全的基础防护用品。传统的人工巡检方式存在效率低、覆盖面有限、易受主观因素影响等问题，难以满足全天候、规模化的安全管理需求。随着深度学习目标检测技术的成熟，利用计算机视觉自动识别防护装备佩戴情况已成为智慧工地与安全生产监管的重要技术手段。

本课题设计并实现了一套基于 YOLOv8 的安全帽/口罩佩戴检测系统。系统以 Ultralytics YOLOv8 为目标检测核心算法，围绕"数据集构建—模型训练—模型评估—检测应用—数据管理"的完整工程链路进行设计，并通过 Flask 框架部署为 Web 应用。主要工作包括：

（1）**数据集构建**。针对安全帽检测，选用公开数据集 keremberke/hard-hat-detection（源自 Roboflow Universe），该数据集采用 COCO JSON 标注格式，共 19,745 张图像；针对口罩检测，选用 face-mask-detection 数据集（PASCAL VOC XML 标注），共 853 张图像。编写了两个格式转换脚本，分别将 COCO JSON 与 PASCAL VOC XML 统一转换为 YOLO 格式的 txt 标注文件，并按 8∶2 与既定的训练/验证划分组织目录结构，最终构建安全帽数据集 19,444 张图像（训练集 15,535 张、验证集 3,909 张）与口罩数据集 853 张图像（训练集 683 张、验证集 170 张）。

（2）**模型训练与评估**。基于 YOLOv8s 预训练权重，在 NVIDIA GeForce RTX 4060 GPU（CUDA 12.4）环境下进行迁移学习训练，输入分辨率 640×640，批量大小 16，训练轮数上限 80，并启用早停机制（patience=20）防止过拟合。训练过程中记录边界框损失、分类损失、DFL 损失以及精确率、召回率、mAP@0.5、mAP@0.5:0.95 等指标的变化曲线。实验结果表明，安全帽检测模型的 mAP@0.5 达到 93.24%，口罩检测模型的 mAP@0.5 达到 93.19%，两类检测均显著优于任务书"mAP 不低于 80%"的技术指标要求。

（3）**Web 应用系统开发**。采用 Flask 框架构建 Web 应用，实现了首页概览、图片/视频检测、摄像头实时检测、检测记录管理、统计报表、模型在线训练、模型评估共 7 个功能页面及配套的 RESTful 接口。检测模块基于 OpenCV 实现图像预处理与视频流逐帧推理，支持单张图片上传检测、视频文件上传检测（后台异步处理并转码为 H.264 格式供浏览器播放）以及摄像头实时视频流检测（MJPEG 流式传输）。检测记录模块基于 SQLite 实现检测结果的持久化存储，支持按来源类型、检测类型、时间范围进行筛选查询与分页展示，并可查看单条记录的目标明细。统计报表模块基于 ECharts 实现检测量趋势、类别分布、来源分布与置信度分布的可视化呈现。

（4）**工程化实践**。针对实际开发中的若干工程问题给出了解决方案：使用 PIL 结合中文字体解决 OpenCV 不支持中文标签绘制的问题；采用子进程与后台线程处理训练、评估与视频检测等耗时任务，避免阻塞 Web 请求；使用线程局部存储（threading.local）的数据库连接与 WAL 模式保证 SQLite 的并发安全；通过 imageio-ffmpeg 将检测结果视频转码为 H.264 编码以适配浏览器播放。

系统测试结果表明，各功能模块运行稳定，图片检测单张耗时约 30 ms 级，视频检测平均单帧处理耗时 26.4 ms（约 38 FPS），摄像头实时检测画面流畅，能够满足实时检测的应用需求。本系统可作为智慧工地、安全生产监管等场景的原型系统，具备进一步工程化推广的价值。

**关键词**：YOLOv8；目标检测；安全帽检测；口罩检测；Flask；深度学习

## 第 1 章 绪论

### 1.1 研究背景与意义

安全生产是国民经济与社会发展的基础保障。在建筑施工、电力检修、矿山开采、生产制造等行业中，高处坠落、物体打击等事故长期居于事故类型的前列，而正确佩戴安全帽是降低此类事故伤害程度最直接、最经济的措施之一。与此同时，在粉尘作业、化工生产以及公共卫生事件防控等场景下，口罩的规范佩戴同样是保障人员健康的重要手段。

然而，在实际生产现场，防护装备佩戴的监管长期依赖人工巡检与视频监控人工回看。这种方式存在以下突出问题：

第一，**监管效率低下**。人工巡检难以覆盖全部作业区域与全部时段，存在大量监管盲区；监控视频的人工回看则需要耗费大量人力，且难以做到实时预警。

第二，**主观因素影响大**。人工判断容易受到疲劳、注意力、经验差异等因素影响，漏检与误检难以避免，监管尺度难以统一。

第三，**数据难以沉淀**。人工巡检结果通常以纸质或口头形式记录，缺乏结构化的数据沉淀，难以支撑后续的统计分析、趋势研判与责任追溯。

近年来，以卷积神经网络为代表的深度学习技术在目标检测领域取得了突破性进展。YOLO（You Only Look Once）系列算法作为单阶段目标检测的代表，在检测精度与推理速度之间取得了良好的平衡，已广泛应用于工业检测、智能交通、安防监控等领域。将 YOLOv8 目标检测技术应用于防护装备佩戴检测，能够实现自动、实时、客观的识别与预警，有效弥补人工监管的不足。

本课题的研究意义主要体现在以下三个方面：

（1）**应用价值**：系统可部署于工地出入口、作业区域等场景的监控系统中，实现防护装备佩戴的自动检测与违规预警，提升安全管理的自动化与智能化水平，降低事故发生风险。

（2）**技术实践价值**：课题覆盖了数据集构建、格式转换、模型训练与调优、模型评估、Web 服务开发、数据库设计与数据可视化等多个环节，是一次完整的机器学习工程实践，有助于系统掌握目标检测应用系统的开发方法。

（3）**数据价值**：系统将每一次检测的结果结构化持久化，形成可查询、可统计的检测记录，为后续的安全态势分析、违规行为溯源提供数据基础。

### 1.2 国内外研究现状

#### 1.2.1 目标检测算法的发展

目标检测旨在从图像中定位并识别出感兴趣的目标，是计算机视觉领域的核心任务之一。其发展历程大致可分为两个阶段。

**传统目标检测阶段**（2014 年以前）主要依赖手工设计的特征描述子与滑动窗口策略。典型的如 Viola-Jones 检测器使用的 Haar 特征与 AdaBoost 分类器，以及 Dalal 与 Triggs 提出的 HOG（方向梯度直方图）特征配合 SVM 分类器。这类方法在受限场景下（如人脸检测）取得了一定效果，但特征表达能力有限，对光照变化、目标形变、遮挡等因素鲁棒性差，难以适应复杂场景。

**基于深度学习的目标检测阶段**（2014 年至今）以卷积神经网络自动学习特征为标志，主流方法分为两条技术路线：

一是**两阶段（two-stage）检测器**，以 R-CNN 系列为代表。Girshick 等人于 2014 年提出 R-CNN，通过选择性搜索生成候选区域，再对每个候选区域进行卷积特征提取与分类；随后提出的 Fast R-CNN 引入 ROI Pooling 实现特征共享，Faster R-CNN 进一步引入区域候选网络（RPN），实现了端到端的训练。两阶段方法检测精度较高，但计算开销大，难以满足实时性要求。

二是**单阶段（one-stage）检测器**，以 YOLO 系列与 SSD 为代表。Redmon 等人于 2016 年提出 YOLOv1，将目标检测转化为回归问题，直接在整张图像上预测边界框与类别概率，大幅提升了检测速度。此后 YOLO 系列不断演进：YOLOv3 引入特征金字塔网络（FPN）实现多尺度检测；YOLOv4 引入 CSPDarknet 骨干网络与 Mosaic 数据增强；YOLOv5 在工程化与易用性方面做了大量优化；YOLOv6、YOLOv7 分别在 industrial 应用与模型结构上持续改进。

**YOLOv8** 由 Ultralytics 公司于 2023 年发布，是当前 YOLO 系列的重要版本。它在结构设计上做出多项改进：采用无锚框（anchor-free）的检测头，减少超参数依赖；引入 C2f 模块替代 C3 模块以丰富梯度流；采用解耦头（decoupled head）结构将分类与回归任务分离；在损失函数上使用 Distribution Focal Loss（DFL）与 CIoU 损失的组合，并采用 Task-Aligned Assigner 进行正负样本分配。这些改进使 YOLOv8 在精度与速度上均优于同期的 YOLOv5 与 YOLOv7，且官方提供了完善的 Python 接口与命令行工具，工程落地门槛低。

#### 1.2.2 防护装备佩戴检测的应用研究

近年来，将目标检测技术应用于防护装备佩戴检测已成为研究热点，相关研究主要集中在以下方向：

一是对通用检测算法的**结构改进**。研究者通过在骨干网络引入注意力机制（如 SE、CBAM 模块）、改进特征融合结构（如 BiFPN）、引入可变形卷积等方式，提升对小目标、密集目标与遮挡目标的检测能力。

二是对**数据增强与样本不平衡**的处理。施工现场存在目标尺度差异大、部分类别样本稀少等问题，研究者通过 Mosaic 增强、混合样本、重采样等方式改善模型的泛化能力。

三是**轻量化与边缘部署**。为满足工地现场的实时性要求，研究者通过模型剪枝、量化、知识蒸馏等手段压缩模型规模，将其部署到嵌入式设备或边缘计算盒子中。

从整体看，已有研究多以算法改进为主，而将检测算法与数据管理、可视化、在线训练等功能整合为完整应用系统的工作相对有限。本课题的定位正是后者：不追求算法结构的创新，而是聚焦于**工程实现的完整性与实用性**，构建一个功能闭环、可直接使用的 Web 应用系统。

## 第 2 章 相关技术基础

### 2.1 YOLOv8 目标检测算法

#### 2.1.1 算法概述

YOLOv8 是 Ultralytics 于 2023 年发布的单阶段目标检测算法，属于"你只需看一次"（You Only Look Once）系列的最新版本之一。与两阶段检测器先生成候选区域再分类的思路不同，单阶段检测器将目标检测建模为一个端到端的回归问题：输入整张图像，网络一次性输出所有目标的边界框坐标与类别概率，因而具有显著的速度优势。

YOLOv8 按模型规模提供了 n、s、m、l、x 五个版本，参数量与计算量依次递增，检测精度依次提升而推理速度依次下降。本系统综合考虑检测精度与推理速度的平衡，选用 **YOLOv8s** 版本。

#### 2.1.2 网络结构

YOLOv8 的网络结构由骨干网络（Backbone）、颈部网络（Neck）与检测头（Head）三部分组成。

**（1）骨干网络（Backbone）**。负责从输入图像中提取多尺度特征。YOLOv8 的骨干网络基于 CSPDarknet 的思想改进而来，核心组成单元是 **C2f 模块**。C2f 模块在 YOLOv5 的 C3 模块基础上进行了调整，通过更多的分支连接与跨阶段部分连接，在保持轻量化的同时丰富了梯度流动路径，增强了特征表达能力。骨干网络的末端采用 **SPPF（Spatial Pyramid Pooling Fast）**模块，通过串联多个最大池化层实现多尺度感受野的特征融合，在减少计算量的同时保持了空间金字塔池化的效果。

**（2）颈部网络（Neck）**。负责将骨干网络提取的多尺度特征进行融合。YOLOv8 采用 **PAN-FPN（Path Aggregation Network with Feature Pyramid Network）**结构，通过自顶向下与自底向上两条路径的双向特征融合，使不同尺度的特征图都能同时获得高层的语义信息与底层的空间细节信息，从而提升对不同尺度目标的检测能力，尤其是小目标的检测效果。

**（3）检测头（Head）**。YOLOv8 采用 **解耦头（Decoupled Head）**结构，将分类任务与边界框回归任务分配到两个独立的分支中分别处理。在早期的 YOLO 版本中，分类与回归共享同一组卷积层，两类任务的优化目标存在差异，容易相互干扰；解耦头结构通过任务分离有效缓解了这一问题，有助于提升收敛速度与检测精度。

此外，YOLOv8 采用了**无锚框（Anchor-Free）**的检测范式。早期版本依赖预先设定的锚框（anchor box）作为回归基准，锚框的尺寸与比例需要针对数据集进行聚类设计，属于较难调优的超参数。无锚框方式直接预测目标边界相对于特征图位置的距离分布，省去了锚框设计环节，降低了对数据集的依赖性，也简化了检测头的输出解析。

#### 2.1.3 损失函数与样本分配

YOLOv8 的训练损失由三部分组成：

（1）**分类损失（cls_loss）**：采用二元交叉熵损失（BCE Loss），衡量预测类别与真实类别的差异。

（2）**边界框回归损失（box_loss）**：采用 CIoU（Complete Intersection over Union）损失。CIoU 在 IoU 的基础上进一步考虑了预测框与真实框的中心点距离以及宽高比的差异，能够更全面地度量边界框的回归质量，加快收敛。

（3）**DFL 损失（dfl_loss）**：Distribution Focal Loss 将边界框位置建模为概率分布，通过学习边界位置周围的分布来提升定位精度，尤其对边界模糊的目标效果明显。

在正负样本分配方面，YOLOv8 采用 **Task-Aligned Assigner（任务对齐分配器）**，根据分类得分与定位质量的联合指标动态地为每个真实目标分配正样本，使分类与回归任务在训练过程中保持一致性。在推理阶段，网络输出大量候选框，通过**非极大值抑制（NMS）**去除重叠的冗余框，保留置信度最高的检测结果。

### 2.2 目标检测评价指标

评价目标检测模型的性能，需要从"是否检出"与"定位是否准确"两个维度综合衡量。本系统采用以下指标：

**（1）IoU（交并比）**。IoU 衡量预测边界框与真实边界框的重合程度，定义为两者交集面积与并集面积之比。通常当 IoU 大于某一阈值（如 0.5）时，认为该预测为正确检测。

**（2）精确率（Precision）与召回率（Recall）**。精确率表示模型检出的目标中真正正确的比例，反映"检出的可信程度"；召回率表示所有真实目标中被正确检出的比例，反映"检出的全面程度"。

**（3）AP 与 mAP**。以精确率为纵轴、召回率为横轴绘制 PR 曲线，曲线下面积即为该类别的平均精度（AP）。对所有类别的 AP 取平均得到平均精度均值（mAP），是衡量目标检测模型综合性能的核心指标。

**（4）mAP@0.5 与 mAP@0.5:0.95**。mAP@0.5 指在 IoU 阈值为 0.5 时计算的 mAP，是衡量检测性能最常用的指标；mAP@0.5:0.95 指在 IoU 阈值从 0.5 到 0.95、步长 0.05 共 10 个阈值下分别计算 mAP 后取平均，对边界框的定位精度要求更为严格。本课题的技术指标"mAP 不低于 80%"采用 mAP@0.5 作为评判标准。

### 2.3 数据集标注格式

目标检测数据集的标注格式主要有三种，本课题涉及其中两种：

**PASCAL VOC 格式**：每张图像对应一个 XML 文件，记录图像尺寸以及每个目标的类别名称与边界框坐标（xmin、ymin、xmax、ymax），坐标为绝对像素值。

**COCO 格式**：整个数据集的所有标注集中存放在一个 JSON 文件中，包含图像信息、类别信息与标注信息，边界框采用 [x, y, width, height] 形式表示左上角坐标与宽高。

**YOLO 格式**：每张图像对应一个同名的 txt 文件，每行描述一个目标，格式为：

```
<class_id> <x_center> <y_center> <width> <height>
```

其中 class_id 为类别索引（从 0 开始），其余四个数值均为相对于图像宽高的归一化值（取值范围 0~1）。YOLO 格式文件简洁、读写高效，是 Ultralytics 框架训练时要求的格式。本课题编写脚本将 COCO JSON 与 VOC XML 统一转换为 YOLO 格式。

### 2.4 其他开发技术

#### 2.4.1 OpenCV

OpenCV 是开源的计算机视觉库，本系统主要使用其以下能力：通过 `cv2.VideoCapture` 读取视频文件与摄像头帧；通过 `cv2.VideoWriter` 写入检测结果视频；通过 `cv2.resize` 进行图像尺寸调整；通过 `cv2.cvtColor` 进行色彩空间转换（YOLO 推理使用 RGB，而 OpenCV 默认读取为 BGR，需要进行转换）。

需要说明的是，OpenCV 的 `cv2.putText` 函数不支持中文字体渲染，直接绘制会出现乱码，本系统通过 PIL 结合系统中文字体解决该问题（详见 5.6.1 节）。

#### 2.4.2 Flask

Flask 是 Python 生态中轻量的 Web 框架，具有核心简洁、扩展灵活的特点。本系统使用 Flask 实现页面路由、文件上传接收、JSON 接口返回等功能。Flask 内置的开发服务器支持多线程模式，能够满足视频检测等异步任务与页面请求的并发处理需求。

#### 2.4.3 SQLite

SQLite 是轻量级的嵌入式关系型数据库，无需独立的数据库服务进程，数据以单文件形式存储，非常适合中小型应用与原型系统。本系统使用 SQLite 存储检测记录，并通过线程局部存储的连接管理与 WAL（Write-Ahead Logging）模式保证多线程环境下的并发安全。

#### 2.4.4 ECharts

ECharts 是开源的可视化图表库，支持折线图、柱状图、饼图等多种图表类型，交互友好。本系统的统计报表模块使用 ECharts 渲染检测量趋势图、类别分布图、来源分布图与置信度分布图。

## 第 3 章 系统需求分析

### 3.1 功能需求分析

根据任务书要求，系统需包含数据集构建、模型训练、模型评估、视频流检测、检测记录管理等功能模块，并通过 Flask 部署为 Web 应用。据此梳理出系统的功能需求如下。

#### 3.1.1 数据集构建需求

系统应提供数据集构建的能力，能够将公开数据集的标注格式（COCO JSON、PASCAL VOC XML）转换为 YOLO 格式，完成训练/验证集划分，并生成符合 Ultralytics 规范的数据配置文件（data.yaml）。具体要求：

（1）支持安全帽与口罩两类数据集的构建；

（2）标注框坐标需正确归一化，类别索引映射正确；

（3）数据集划分需采用固定随机种子，保证结果可复现；

（4）需输出数据集的规模统计（图像数、各类别标注框数量）。

#### 3.1.2 模型训练需求

系统应提供模型训练能力，既支持命令行脚本训练，也支持在 Web 界面中发起训练并实时查看进度。具体要求：

（1）支持设置训练轮数、批量大小、输入分辨率、模型规模等参数；

（2）训练过程中需实时展示损失曲线与 mAP 曲线；

（3）需展示训练日志输出；

（4）训练结束后自动保存最优权重，并可一键部署为线上推理模型；

（5）支持查看历史训练记录。

#### 3.1.3 模型评估需求

系统应能对训练得到的模型进行量化评估。具体要求：

（1）计算精确率、召回率、mAP@0.5、mAP@0.5:0.95 等整体指标；

（2）计算每个类别的独立指标；

（3）生成并展示混淆矩阵与 PR 曲线；

（4）评估结果需持久化保存，供页面随时查看。

#### 3.1.4 检测功能需求

系统应支持三种检测方式：

（1）**图片检测**：用户上传单张图片，系统返回检测结果，在图片上绘制边界框与中文类别标签，并展示检出的目标数量、各类别数量、置信度与推理耗时。

（2）**视频检测**：用户上传视频文件，系统在后台逐帧推理，实时反馈处理进度，完成后输出标注后的视频供在线播放，并将本次检测的汇总结果存入数据库。

（3）**摄像头实时检测**：调用本机摄像头，实时逐帧推理并以视频流形式在页面中展示，支持切换检测类型（安全帽/口罩）与抓拍保存当前帧。

#### 3.1.5 检测记录管理需求

系统应能对检测记录进行持久化管理。具体要求：

（1）每条检测（图片、视频、摄像头抓拍）均生成一条记录，包含时间、来源类型、来源名称、检测类型、目标数量、各类别数量、平均置信度、推理耗时、结果文件路径与目标明细；

（2）支持按来源类型、检测类型、时间范围进行筛选查询；

（3）支持分页浏览、查看详情、单条删除与批量删除。

#### 3.1.6 统计报表需求

系统应对检测记录进行统计分析并可视化。具体要求：

（1）展示累计检测次数、累计目标数、违规目标数、平均置信度等概览指标；

（2）按日期展示检测量趋势；

（3）展示各类别目标的分布；

（4）展示不同来源（图片/视频/摄像头）的分布；

（5）展示置信度区间分布。

### 3.2 非功能需求分析

**（1）性能需求**。模型检测需满足实时性要求：单张图片推理耗时应在百毫秒级；视频检测应能达到接近实时的处理速度；摄像头实时检测画面应无明显卡顿。系统技术指标要求两类检测的 mAP@0.5 不低于 80%。

**（2）易用性需求**。界面设计应美观、布局清晰、操作流畅；上传操作应支持点击选择与拖拽两种方式；检测结果应直观呈现，关键数据一目了然。

**（3）可靠性需求**。耗时操作（训练、评估、视频检测）应异步执行，不得阻塞页面响应；任务执行失败时应给出明确的错误提示而非崩溃；检测记录应可靠持久化。

**（4）可维护性与可扩展性需求**。系统应采用模块化设计，各功能职责清晰；模型采用配置化定义，新增检测类别时只需增加配置与对应权重，无需改动核心推理逻辑。

### 3.3 可行性分析

**（1）技术可行性**。YOLOv8 由 Ultralytics 官方维护，提供了完善的训练与推理接口，文档与社区资源丰富；Flask、OpenCV、SQLite、ECharts 均为成熟稳定的开源技术；本地具备支持 CUDA 的 NVIDIA 显卡，能够满足模型训练与推理的算力需求。技术路线成熟，不存在难以逾越的技术障碍。

**（2）数据可行性**。安全帽与口罩检测均有高质量的公开数据集可供使用，标注规范、样本量充足，能够满足模型训练的基本需求。

**（3）经济可行性**。全部技术栈均为开源软件，无需支付授权费用；训练与推理均在本地 GPU 上完成，无需支付云计算费用。

**（4）时间可行性**。系统功能模块边界清晰，可按照"数据集—模型—Web 应用—测试"的顺序分步实施，各阶段产出明确，能够在规定周期内完成。

## 第 4 章 系统设计

### 4.1 总体架构设计

系统采用分层架构设计，自顶向下分为表现层、应用层、服务层与数据层，如图 4-1 所示（文字描述）。

**表现层**：由 7 个 HTML 页面模板与一套统一的 CSS 样式组成，负责界面呈现与用户交互。前端通过原生 JavaScript 调用后端接口，使用 ECharts 渲染图表。

**应用层**：基于 Flask 的路由与控制器，负责接收 HTTP 请求、校验参数、调用服务层功能并返回 JSON 或渲染页面。包含检测、摄像头、记录、统计、训练、评估六组接口。

**服务层**：封装核心业务逻辑，包括检测推理模块（detector）、视频任务模块（video_jobs）、摄像头模块（camera）、训练管理模块（train_manager）与数据库模块（db）。

**数据层**：包括文件系统（上传文件、检测结果图片与视频）与 SQLite 数据库（检测记录）。

模型层作为独立组成部分，包含预训练权重、训练产出权重以及部署权重，由检测推理模块与训练管理模块共同使用。

系统总体架构的分层关系可概括为：

```
表现层（HTML + CSS + JavaScript + ECharts）
        ↕  HTTP / AJAX
应用层（Flask 路由与控制器）
        ↕
服务层（detector / video_jobs / camera / train_manager / db）
        ↕
数据层（SQLite 数据库 + 文件系统）
        ↕
模型层（YOLOv8 权重：pretrained / runs / models）
```

### 4.2 功能模块设计

系统划分为以下功能模块：

**（1）数据集构建模块**。包含两个独立脚本：`prepare_helmet.py` 负责将 COCO JSON 格式的安全帽数据集转换为 YOLO 格式；`prepare_mask.py` 负责将 PASCAL VOC XML 格式的口罩数据集转换为 YOLO 格式并完成 8∶2 划分。两个脚本均支持幂等执行（已存在的文件自动跳过），并输出规模统计。

**（2）模型训练模块**。包含命令行脚本 `train/train.py` 与 Web 端管理模块 `train_manager.py`。前者封装 Ultralytics 训练接口，支持通过命令行参数配置数据集、模型规模、训练轮数、批量大小、输入分辨率等，训练结束后自动将最优权重复制到部署目录；后者在 Web 端以子进程方式启动训练，将日志写入文件并解析训练过程 CSV，向前端提供进度、损失曲线与 mAP 曲线数据。

**（3）模型评估模块**。包含命令行脚本 `train/val.py` 与 Web 端评估接口。评估脚本调用模型的验证接口计算各项指标，将整体指标与分类别指标写入 JSON 文件，同时生成混淆矩阵与 PR 曲线图片供页面展示。

**（4）检测推理模块**。封装于 `detector.py`，提供统一的图像推理接口：接收图像数据与检测类型，返回目标列表（类别、置信度、边界框坐标）、各类别计数、绘制标注后的图像以及推理耗时。模块内置模型缓存，避免重复加载；通过配置文件定义模型类别与中文名称。

**（5）视频检测模块**。封装于 `video_jobs.py`，以后台线程方式逐帧读取视频并推理，将进度写入任务字典供前端轮询，处理完成后调用 ffmpeg 将结果视频转码为 H.264 编码，并将汇总结果写入数据库。

**（6）摄像头模块**。封装于 `camera.py`，以单例线程方式持续采集摄像头画面并推理，通过 MJPEG（multipart/x-mixed-replace）流式传输给前端；支持按最小时间间隔自动落库，避免记录爆炸；支持抓拍当前帧。

**（7）检测记录管理模块**。封装于 `db.py`，提供记录的插入、分页查询、条件筛选、详情查询、单条删除与批量删除，以及多维度统计聚合。

**（8）统计报表模块**。后端提供统计聚合接口，前端使用 ECharts 渲染检测量趋势、类别分布、来源分布与置信度分布四类图表。

（1）**系统首页**：展示系统介绍、功能入口卡片与整体运行概况。

（2）**检测中心**：采用标签页区分图片检测与视频检测。图片检测区展示上传区、置信度阈值滑杆、检测类型选择，结果区并排展示标注后的原图与检出目标列表；视频检测区展示上传区与处理进度，完成后提供视频播放器与汇总统计。

（3）**实时摄像头**：主体为视频流显示区，提供检测类型切换、开始/停止、抓拍等控制按钮，并展示当前帧的检出统计。

（4）**检测记录**：顶部为筛选区（来源类型、检测类型、时间范围），主体为记录表格（缩略图、时间、来源、类型、各类别数量、置信度、耗时、操作），支持分页、查看详情与批量删除。

（5）**统计报表**：顶部为概览指标卡片，主体为四个图表区域。

（6）**模型训练**：包含训练参数表单、实时损失与 mAP 曲线、训练日志滚动区域以及历史训练记录列表（支持一键部署）。

（7）**模型评估**：展示评估指标卡片、分类别指标表格以及混淆矩阵与 PR 曲线图片。


## 第 5 章 系统实现

### 5.1 数据集构建的实现

#### 5.1.1 安全帽数据集

安全帽数据集选用公开数据集 `keremberke/hard-hat-detection`（源自 Roboflow Universe 的 "Hard Hats" 数据集），该数据集以 COCO JSON 格式标注，原始划分为 train（13,782 张）、valid（3,962 张）、test（2,001 张），共 19,745 张图像。

数据集构建脚本 `datasets/prepare_helmet.py` 的处理流程如下：

（1）**解析 COCO 标注**。读取各分包对应的 JSON 文件，提取图像尺寸信息与标注信息。COCO 的边界框格式为 `[x, y, width, height]`（左上角坐标与宽高的绝对像素值），需转换为 YOLO 格式的中心点坐标与宽高，并除以图像宽高完成归一化。

（2）**类别映射**。原数据集中 `hardhat` 类别映射为 YOLO 类别 0（helmet，安全帽），`no-hardhat` 类别映射为 YOLO 类别 1（head，未戴安全帽）。

（3）**划分合并**。按照"train + test 合并为训练集、valid 作为验证集"的策略组织，以充分利用标注数据。

（4）**文件复制与标注写入**。将图像复制到目标目录，并为每张图像生成同名的 txt 标注文件。脚本采用幂等设计：若目标文件已存在则跳过，支持中断后继续运行；文件复制操作增加了重试机制以应对文件系统的临时占用。

（5）**统计输出**。统计并输出图像总数与各类别标注框数量，同时生成 `data.yaml` 配置文件。

构建结果：共生成 19,444 张图像（训练集 15,535 张、验证集 3,909 张），其中 helmet 类别标注框 42,326 个、head 类别标注框 12,935 个。

#### 5.1.2 口罩数据集

口罩数据集选用公开数据集 `face-mask-detection`（即经典的 maksssksksss 数据集），共 853 张图像，采用 PASCAL VOC XML 格式标注，每张图像对应一个同名 XML 文件。

数据集构建脚本 `datasets/prepare_mask.py` 的处理流程如下：

（1）**原始数据获取**。脚本内置下载函数，通过 `huggingface_hub` 从镜像站点拉取原始数据；考虑到国内网络环境下 HTTPS 代理易出现连接异常，实际实施中采用了基于 URL 清单的并行下载方式，确保 853 张图像全部下载完整。

（2）**解析 VOC 标注**。解析每个 XML 文件，读取图像宽高以及每个目标的类别名称与边界框坐标（xmin、ymin、xmax、ymax），转换为 YOLO 的归一化中心点坐标与宽高格式。

（3）**类别映射**。原数据集包含三个类别：`with_mask`（正确佩戴口罩）映射为 YOLO 类别 0（mask）；`without_mask`（未佩戴口罩）与 `mask_weared_incorrect`（口罩佩戴不规范）均映射为 YOLO 类别 1（face）。将"佩戴不规范"归入未佩戴类别，是因为从安全管理角度看，佩戴不规范同样不具备有效防护作用，应作为违规情形予以提示。

（4）**数据集划分**。按 8∶2 的比例随机划分为训练集与验证集，随机种子固定为 42，保证划分结果可复现。

（5）**输出与统计**。生成目录结构与 `data.yaml` 配置文件，输出规模统计。

构建结果：共 853 张图像（训练集 683 张、验证集 170 张），其中 mask 类别标注框 3,229 个、face 类别标注框 840 个。

#### 5.1.3 数据配置文件

两个数据集均生成符合 Ultralytics 规范的 `data.yaml` 文件，其内容包括数据集根路径、训练集与验证集的相对路径、类别数量 `nc` 以及类别名称列表 `names`。示例如下：

```yaml
path: ./
train: images/train
val: images/val
nc: 2
names:
  0: helmet
  1: head
```

### 5.2 模型训练的实现

#### 5.2.1 训练脚本

训练脚本 `train/train.py` 封装了 Ultralytics 的训练接口，支持通过命令行参数配置训练过程，主要参数包括数据集路径（`--data`）、预训练权重（`--model`）、训练轮数（`--epochs`，默认 80）、输入分辨率（`--imgsz`，默认 640）、批量大小（`--batch`，默认 16）、训练设备（`--device`）、数据加载线程数（`--workers`）、运行名称（`--name`）以及部署名称（`--deploy-name`）。

训练完成后，脚本自动将本次运行产出目录下的 `best.pt`（验证集指标最优的权重）复制到 `models/` 目录下并以部署名称命名，供 Web 应用直接加载使用，实现了训练到部署的衔接。

#### 5.2.2 训练超参数配置

综合显卡显存容量（8 GB）、数据集规模与训练时间成本，确定训练超参数如表 5-1 所示。

**表 5-1 模型训练超参数**

| 参数 | 取值 | 说明 |
| :--- | :--- | :--- |
| 基础模型 | YOLOv8s | 精度与速度均衡 |
| 预训练权重 | yolov8s.pt | 基于 COCO 数据集的预训练权重 |
| 输入分辨率 | 640 × 640 | Ultralytics 默认分辨率 |
| 批量大小 | 16 | 适配 8 GB 显存 |

| 训练设备 | GPU 0 | NVIDIA RTX 4060 |

采用迁移学习策略：加载在大规模 COCO 数据集上预训练的权重作为初始化，再在本课题的专用数据集上进行微调。这样做能够显著加快收敛速度，并在专用数据集规模有限（尤其是口罩数据集仅 853 张）的情况下获得更好的泛化性能。

#### 5.2.3 Web 端训练管理

Web 端的训练功能由 `train_manager.py` 实现，其核心设计如下：

（1）**子进程执行**。训练任务通过 `subprocess.Popen` 启动独立的 Python 子进程执行，避免长时间占用 Web 请求线程，也便于任务的管理与终止。

（2）**环境隔离**。为子进程设置独立的环境变量，指定项目内独立的 matplotlib 缓存目录。这一处理源于实际开发中遇到的问题：Ultralytics 在初始化时会清理 matplotlib 的字体缓存文件，在受保护的运行环境中该删除操作可能被拦截并导致训练中断；通过指定独立的缓存目录规避了这一问题。

（3）**进度解析**。训练过程中 Ultralytics 会将每轮的损失与指标写入 CSV 文件，管理模块定时解析该文件，提取轮次、训练损失（box/cls/dfl）、精确率、召回率、mAP@0.5、mAP@0.5:0.95 等数据，供前端绘制实时曲线。

（4）**日志采集**。子进程的标准输出实时写入日志文件，前端可滚动查看最新日志内容。

（5）**历史与部署**。管理模块扫描运行目录，列出所有历史训练记录及其最优指标，支持将任一历史权重一键部署为线上推理模型，部署后立即清除模型缓存以使新权重生效。

### 5.3 检测推理模块的实现

检测推理模块 `detector.py` 是系统的核心，其对外提供的主接口为图像推理函数，接收图像数据（BGR 格式的 NumPy 数组）、检测类型列表与置信度阈值，返回四项结果：目标列表、各类别计数、绘制标注后的图像、推理耗时。

模块的实现要点包括：

**（1）模型缓存与按需加载**。模块维护一个模型缓存字典，首次使用某一检测类型时加载对应权重，后续请求直接复用，避免重复加载带来的时间开销。权重文件的查找顺序为：优先查找 `models/` 目录（已部署的正式权重），若不存在则回退到 `runs/` 目录下的训练产出。若两者均不存在，则抛出模型缺失异常，由上层捕获并返回友好的中文提示，引导用户先完成训练或部署。

**（2）多类型联合检测**。系统支持在一次请求中同时检测多个类型（如同时检测安全帽与口罩）。实现上对每个类型分别调用对应模型推理，再合并结果。

**（3）类别计数与数据库字段映射**。检测结果的类别计数（如 helmet、head）需要映射到数据库记录的对应字段列。模块提供专门的转换函数，将类别计数转换为数据库字段字典，未出现的类别补零。

**（4）标注绘制与中文标签**。检测结果需要在图像上绘制边界框与类别标签。OpenCV 自带的文字绘制函数不支持中文字符，直接使用会出现乱码。解决方案是：先用 OpenCV 绘制边界框矩形，再使用 PIL（Python Imaging Library）加载系统中文字体绘制中文标签文字。标签内容包含中文类别名称与置信度数值，背景色按类别区分，保证可读性。

**（5）耗时统计**。使用高精度计时器记录单次推理耗时，作为性能数据返回并存入数据库。

### 5.4 视频检测的实现

视频检测由 `video_jobs.py` 实现，采用"后台线程 + 任务状态字典 + 前端轮询"的异步模式，避免长时间阻塞 HTTP 请求。

处理流程如下：

（1）**任务创建**。接收上传的视频文件并保存到上传目录，生成唯一的任务 ID，初始化任务状态（状态为进行中、进度为 0），随后启动后台线程处理。

（2）**逐帧推理**。线程中通过 `cv2.VideoCapture` 打开视频，读取视频的帧率、总帧数、宽高信息；若视频分辨率超过设定的最大边长（1,280 像素），按比例缩放以控制处理开销；创建视频写入器，逐帧读取、调用检测推理、将标注后的帧写入临时视频文件。

（3）**进度更新**。每处理一帧即更新任务状态中的已处理帧数与进度百分比，前端通过定时轮询接口获取进度并实时展示。

（4）**结果汇总**。处理过程中累计各类别检出数量、置信度总和、推理耗时总和，并按固定时间间隔抽样保存部分帧的目标明细，供后续查看详情使用。

（5）**视频转码**。OpenCV 默认写出的视频采用 mp4v 编码，浏览器无法直接播放；处理完成后调用 ffmpeg 将临时视频转码为 H.264 编码（yuv420p 像素格式，并启用 faststart 以支持边加载边播放），输出为最终结果视频。

（6）**落库与状态更新**。将本次检测的汇总结果写入数据库生成检测记录，随后更新任务状态为完成，并返回结果视频的访问路径、检出统计与平均单帧耗时。

（7）**异常处理**。整个处理过程包裹异常捕获，一旦出现错误（如视频无法打开、编码器初始化失败）即更新任务状态为失败并记录错误信息，供前端提示用户。

### 5.5 摄像头实时检测的实现

摄像头实时检测由 `camera.py` 实现，采用"单例采集线程 + MJPEG 流式传输"的方案。

**（1）采集与推理线程**。模块维护一个全局唯一的采集线程，线程中循环执行：打开摄像头、读取一帧、调用检测推理、保存标注后的帧与当前检出统计。线程按需启动，页面请求视频流时自动开启。

**（2）MJPEG 流式传输**。Flask 的响应可以直接返回一个生成器函数，配合 `multipart/x-mixed-replace` 内容类型，即可实现 MJPEG 视频流。模块中的生成器不断从线程获取最新的标注帧，编码为 JPEG 后按约定的分隔符组装成数据帧输出。浏览器端的 `<img>` 标签指向该接口地址即可持续刷新显示，无需额外插件。

**（3）自动落库与防抖**。为避免持续检测产生海量记录，模块设置最小落库间隔（5 秒）：仅当当前帧检出目标且距上次落库超过设定间隔时，才生成一条检测记录。

**（4）抓拍功能**。提供抓拍接口，将当前帧保存为图片并生成一条检测记录，便于事后查看与取证。

**（5）状态查询与类型切换**。提供摄像头状态查询接口（是否开启、当前检测类型、最近检出统计）与检测类型切换接口。

### 5.6 检测记录与统计报表模块的实现

#### 5.6.1 记录管理

`db.py` 封装了全部数据库操作：

（1）**连接管理**。采用线程局部存储，为每个线程创建并持有独立的数据库连接，避免多线程共享连接引发的异常；启用 WAL 模式提升读写并发能力。

（2）**记录插入**。提供统一的插入接口，接收关键字参数构造插入语句。目标明细字段以列表或字典形式传入，在插入前统一序列化为 JSON 字符串存储。

（3）**条件查询与分页**。查询接口支持来源类型、检测类型、起始日期、结束日期等筛选条件，动态拼接 SQL 语句；支持分页参数，同时返回符合条件的总条数以便前端计算页码。

（4）**详情与删除**。支持按主键查询单条记录详情（返回时反序列化目标明细），支持单条删除与批量删除。

（5）**统计聚合**。提供多组统计查询：概览统计（累计检测次数、累计目标数、各类别总数、平均置信度）、按日期的检测量趋势、类别分布、来源分布以及置信度区间分布。

#### 5.6.2 统计报表

统计报表页面在加载时调用统计接口获取数据，使用 ECharts 渲染四类图表：检测量趋势折线图（按日期）、类别分布柱状图或饼图、来源分布饼图、置信度区间分布柱状图。页面顶部以卡片形式展示关键概览指标。图表库文件已本地化部署，避免因网络环境导致的加载失败。

### 5.7 关键技术与难点

在实际开发过程中遇到并解决了以下技术难点：

**（1）OpenCV 不支持中文标签绘制**。OpenCV 的 `putText` 仅支持 ASCII 字符集。解决方案是采用 PIL 绘制：将 OpenCV 的图像数组转换为 PIL 图像对象，使用系统中文字体（`msyh.ttc`）绘制标签文字与背景，再转换回 OpenCV 数组格式。

**（2）浏览器无法播放 OpenCV 输出的视频**。OpenCV 的 VideoWriter 在 Windows 环境下默认使用 mp4v 编码，主流浏览器不支持。解决方案是在处理完成后调用 ffmpeg（由 `imageio-ffmpeg` 提供可执行文件，无需单独安装）转码为 H.264 编码。

**（3）耗时任务阻塞 Web 请求**。训练、评估与视频检测均为耗时操作。解决方案是：训练与评估使用独立子进程，视频检测使用后台线程，均通过状态查询接口由前端轮询获取进度，主线程始终保持响应。

**（4）SQLite 多线程并发访问**。Flask 多线程模式下多个线程同时访问数据库易引发异常。解决方案是采用线程局部存储为每线程分配独立连接，并启用 WAL 模式。

**（5）深度学习框架的缓存清理被安全策略拦截**。Ultralytics 初始化时会清理 matplotlib 的字体缓存文件，在受保护环境中该删除操作会被拦截并中断训练。解决方案是为训练子进程指定项目内独立的 matplotlib 缓存目录。

**（6）中间文件的清理不应影响任务结果**。视频检测处理完成后需删除临时视频文件，若删除操作因文件占用或权限原因失败，不应导致整个任务被判定为失败。解决方案是将删除操作封装为"安全删除"函数（内部捕获并忽略异常），并将其置于任务状态更新之后执行。

**（7）国内网络环境下数据集下载不稳定**。HuggingFace 官方站点在国内访问缓慢，且通过 Python HTTP 客户端下载时易出现代理错误。解决方案是使用国内镜像站点，并采用基于 URL 清单的并行下载方式，同时支持断点续传（已存在且大小正常的文件自动跳过）。

| 17 | 1.335 | 0.776 | 1.197 | 0.879 | 0.887 | 0.917 | 0.562 |
| 22 | 1.312 | 0.743 | 1.178 | 0.891 | 0.896 | 0.930 | 0.573 |
| 27 | 1.288 | 0.711 | 1.167 | 0.896 | 0.897 | 0.932 | 0.582 |

从训练过程可以看出：三项训练损失（box、cls、dfl）均持续稳定下降，说明模型在有效学习；各项精度指标则持续爬升——mAP@0.5 从首轮的 0.849 逐步提升至第 27 轮的 0.932。训练至第 27 轮后指标进入平台期（后续轮次的提升不足 0.1 个百分点），验证集最优模型出现在第 27 轮，故取该轮权重作为最终模型。整个训练在 RTX 4060 GPU 上约耗时 1.7 小时（每轮约 220 秒）。

训练完成后，系统在验证集上的最终评估指标将在模型评估环节给出（见 6.3 节）。

#### 6.2.2 口罩检测模型

口罩检测模型基于 YOLOv8s 在 853 张图像的数据集上训练，训练集 683 张、验证集 170 张，采用与安全帽模型相同的超参数配置（输入分辨率 640、批量大小 16、轮数上限 80、早停耐心值 20）。

由于口罩数据集规模较小，迁移学习的作用更为关键：借助在 COCO 数据集上预训练的权重，模型首轮验证 mAP@0.5 即达到 0.697，第 10 轮提升至 0.865，第 20 轮达到 0.906；此后提升放缓，验证集最优模型出现在第 55 轮（mAP@0.5 = 0.932）。训练在触发早停条件后于第 75 轮停止，共训练 75 轮、耗时约 13.5 分钟。最终评估指标见 6.3 节。

### 6.6 结果分析

综合上述测试结果，可以得出以下结论：

（1）**功能完整性**。系统实现了任务书要求的全部功能模块：数据集构建、模型训练、模型评估、视频流检测（含图片、视频、摄像头三种方式）、检测记录管理，并额外提供了统计报表功能，形成了"数据—模型—应用—反馈"的完整闭环。

（2）**指标达标性**。两类检测的 mAP@0.5 均达到 93% 以上，显著超过 80% 的技术指标要求；其中口罩模型对"正确佩戴口罩"类别的 mAP@0.5 高达 0.975，具备很强的实用价值。

（3）**性能可用性**。单帧推理耗时在 30 ms 级，视频处理约 38 FPS，摄像头实时检测画面流畅，满足实时性要求。

（4）**存在的不足**。一是安全帽数据集中 head 类别（未戴安全帽）的样本量（12,935 个标注框）明显少于 helmet 类别（42,326 个），存在一定程度的类别不平衡；二是口罩数据集规模较小（853 张），且 face 类别的验证集实例较少（133 个），其召回率（0.841）相对 mask 类别（0.960）偏低，模型的泛化能力受限于数据多样性；三是模型未做轻量化处理，在低算力设备上部署存在困难。

## 第 7 章 总结与展望

### 7.1 总结

本课题围绕"基于 YOLOv8 的安全帽/口罩佩戴检测系统"展开设计与实现，完成了从数据集构建到 Web 应用部署的完整开发流程。主要工作总结如下：

（1）完成了两类数据集的构建。调研并获取了安全帽与口罩的公开数据集，分别将 COCO JSON 与 PASCAL VOC XML 标注格式转换为 YOLO 格式，完成了数据集的划分与组织，为模型训练奠定了数据基础。

（2）完成了两个检测模型的训练与评估。基于 YOLOv8s 预训练权重，在 GPU 环境下完成迁移学习训练，训练过程中实时监控损失与精度指标变化，两类模型的 mAP@0.5 分别达到 93.24%（安全帽）与 93.19%（口罩），显著优于任务书 80% 的技术指标要求。

（3）完成了 Web 应用系统的开发。基于 Flask 框架实现了 7 个功能页面与配套接口，支持图片检测、视频检测与摄像头实时检测三种检测方式，实现了检测记录的持久化管理与多维度统计可视化，并提供了在线模型训练与评估能力。

（4）解决了一系列工程实现问题，包括中文标签绘制、视频编码转码、耗时任务异步化、数据库并发安全、数据集下载稳定性等，积累了较为完整的工程实践经验。

通过本课题的实践，系统掌握了 YOLOv8 目标检测算法的原理与训练流程，熟悉了计算机视觉与视频流处理的关键技术，提升了目标检测应用系统的设计与实现能力，也在数据集构建与模型调优方面积累了实际经验。

### 7.2 展望

受时间与条件限制，本系统仍存在可改进的空间，后续可从以下方向进一步完善：

（1）**扩充与优化数据集**。针对类别不平衡问题，可通过增补未佩戴类别的样本、采用过采样或类别加权等方式改善；针对口罩数据集规模偏小的问题，可扩充更多场景、更多光照与遮挡条件下的样本，提升模型泛化能力。

（2）**引入目标跟踪与行为分析**。在检测基础上引入多目标跟踪算法（如 ByteTrack），对同一人员跨帧关联，可实现"违规持续时长"的判定，减少瞬时误判，进一步支撑预警策略的制定。

（3）**模型轻量化与边缘部署**。通过模型剪枝、量化（如 FP16/INT8）、知识蒸馏等手段压缩模型，或改用 YOLOv8n 等更小规模的版本，将系统部署到边缘计算设备，降低对中心服务器的依赖。

（4）**完善预警与联动机制**。接入实时告警推送（如语音提示、消息通知），并与门禁、考勤等业务系统联动，形成"检测—预警—处置—复核"的管理闭环。

（5）**增强系统安全性与多用户支持**。引入用户认证与权限管理，支持多用户、多工地的数据隔离，并补充操作日志审计，以满足实际生产环境的管理需求。
