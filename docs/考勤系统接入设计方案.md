# 考勤系统接入设计方案

> 本文是**设计方案**，不是使用说明。目的是把「基于人脸识别做考勤」这件事的
> 数据模型、判定规则、风险边界和分阶段计划讲清楚，供实现前评审与后续开发参照。
>
> 结论先行：**可以做，但必须明确定位为「辅助考勤 / 在岗统计」，
> 不能当作严格考勤依据** —— 理由见第三节。

---

## 一、为什么顺势做考勤：现有基础已经覆盖七成

系统已经具备考勤所需的核心能力，缺的主要是「时间维度的解释层」：

| 考勤需要什么 | 现有基础 | 缺口 |
|---|---|---|
| 认出「这是谁」 | `face_persons` 底库 + `face_db.identify()`，512 维特征、阈值 0.38 | 无 |
| 记录「什么时间出现过」 | `face_seen` 已有 `created_at`（精确到秒） | 无 |
| 知道「当时装备是否合规」 | `face_seen.hat_state` / `mask_state`（三态） | 无 |
| 区分来源（哪个摄像头/手机） | `face_seen.source` | 需扩展为摄像头 id |
| 判定「上班 / 下班」 | — | **需要班次规则** |
| 算「工时」 | — | **需要签到签退配对** |
| 处理「一天来很多次」 | — | **需要会话归并** |
| 处理「迟到 / 早退 / 缺勤」 | — | **需要班次 + 判定规则** |

**关键洞察**：`face_seen` 本质上已经是一份**带秒级时间戳的到岗流水**。
考勤不是新采集数据，而是**对已有流水做规则化的再解释**。
这意味着第一阶段几乎不需要改识别链路，这在工程上是非常划算的。

## 二、数据模型设计

### 2.1 班次定义表 `att_shifts`

不同岗位上下班时间不同，必须可配置，不能写死。

```sql
CREATE TABLE IF NOT EXISTS att_shifts (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    name          TEXT NOT NULL,          -- 班次名，如「白班」「夜班」
    start_time    TEXT NOT NULL,          -- 'HH:MM' 上班时间
    end_time      TEXT NOT NULL,          -- 'HH:MM' 下班时间
    -- 宽限分钟：上班后多少分钟内不算迟到
    late_grace    INTEGER DEFAULT 5,
    -- 早退宽限：下班前多少分钟内走不算早退
    early_grace   INTEGER DEFAULT 5,
    -- 跨天班次（夜班 22:00-06:00）时必须置 1，否则时长会算成负数
    cross_day     INTEGER DEFAULT 0,
    -- 工作日掩码：'1,1,1,1,1,0,0' = 周一到周五
    workdays      TEXT DEFAULT '1,1,1,1,1,0,0',
    created_at    TEXT NOT NULL
);

-- 人员与班次的绑定。不绑定时用 default 班次
CREATE TABLE IF NOT EXISTS att_assignments (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    person_id   INTEGER NOT NULL,          -- 指向 face_persons.id
    shift_id    INTEGER NOT NULL,          -- 指向 att_shifts.id
    -- 生效区间：支持调岗、换班
    effective_from TEXT NOT NULL,
    effective_to   TEXT,
    created_at  TEXT NOT NULL
);
```

### 2.2 考勤日结表 `att_daily`

**这是考勤的核心表**。原始流水（`face_seen`）是「事实」，
日结是「对事实的解释」—— 两者必须分开存：

- 流水可能被清理 / 过期删除，但考勤结果必须长期保留（劳动法相关，至少存 2 年）
- 规则会变（比如改了迟到宽限），日结可以按新规则重算，不影响原始流水
- 日结表可以直接被报表、导出、对账消费，不必每次重算全量流水

```sql
CREATE TABLE IF NOT EXISTS att_daily (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    person_id     INTEGER NOT NULL,
    person_name   TEXT NOT NULL,          -- 冗余存一份：底库改名/删人后历史仍可追溯
    work_date     TEXT NOT NULL,          -- 'YYYY-MM-DD'，归属日（已按跨天班次归一）
    shift_id      INTEGER,

    first_seen    TEXT,                   -- 当天首次识别时间（签到）
    last_seen     TEXT,                   -- 当天末次识别时间（签退）
    seen_count    INTEGER DEFAULT 0,      -- 当天识别总次数
    work_minutes  INTEGER DEFAULT 0,      -- 在岗时长（分钟）

    status        TEXT,                   -- normal / late / early_leave / absent / incomplete
    late_minutes  INTEGER DEFAULT 0,
    early_minutes INTEGER DEFAULT 0,

    -- 装备合规汇总（与考勤同源，方便一张表出「考勤+安全」综合报表）
    hat_bad       INTEGER DEFAULT 0,
    mask_bad      INTEGER DEFAULT 0,

    computed_at   TEXT NOT NULL,
    UNIQUE(person_id, work_date)          -- 一人一天一条，重复结算走 UPSERT
);
CREATE INDEX IF NOT EXISTS idx_att_daily_date ON att_daily(work_date);
CREATE INDEX IF NOT EXISTS idx_att_daily_person ON att_daily(person_id);
```

### 2.3 为什么不用「签到/签退」两张表

直觉上会想建 `att_checkin` / `att_checkout` 两张表，但这里**刻意不这么做**：

- 人脸识别是**持续识别**，不是用户主动刷卡 —— 一个人 8:05、8:07、8:20
  都会被识别到，无法判断哪一次是「签到」、哪一次是「签退」；
- 真正的语义是「从首次出现到末次离开」这一**区间**，
  所以「首次时间 / 末次时间」两个字段比两张表更贴合事实；
- 表结构简单，避免了「有签到没签退」这类脏状态。

> 这也决定了后面第三节的结论：视频考勤天生只能算「在岗时长」，
> 不能算「精确打卡时刻」。

## 三、判定规则

### 3.1 会话归并（把碎片流水合成「一次在场」）

**问题**：一个人在镜头前待 10 分钟，可能被识别 30 次。这 30 条记录是
「一次在场」还是「30 次到岗」？必须按时间间隔归并。

```
规则：把同一人的识别记录按时间排序，
      相邻两条间隔 > SESSION_GAP（默认 30 分钟）视为「离开又回来」，切成两段；
      间隔 ≤ SESSION_GAP 视为同一次在场。

为什么取 30 分钟：
  - 太短（如 5 分钟）：去趟洗手间就被拆成两次，签到签退会乱
  - 太长（如 2 小时）：午休外出、下午回来会被合成一段，工时虚高
  30 分钟是「短时离开」与「长时间不在」的一个实用分界。
```

### 3.2 签到 / 签退的确定

```
签到时间 = 当天该人「第一条」会话的开始时间
签退时间 = 当天该人「最后一条」会话的结束时间
在岗时长 = 各会话时长之和（不是签退 - 签到，否则午休会被算成工时）
```

⚠️ 这里有个**故意的取舍**：用「会话时长之和」而不是「首末相减」，
意味着午休 1 小时不计入工时。这更接近真实在岗时间，
但会让「工时」小于「首末跨度」—— 报表上必须同时展示两者，
否则用户会以为算错了。

### 3.3 状态判定

```
设班次 [B_start, B_end]，宽限 g_late / g_early

正常    ： first_seen <= B_start + g_late  且  last_seen >= B_end - g_early
迟到    ： first_seen >  B_start + g_late
早退    ： last_seen  <  B_end   - g_early
迟到+早退：两者同时满足（status 仍记 'late'，但 early_minutes > 0）
缺勤    ： 当天无任何记录，且是工作日
记录不全： 有记录但只在半天（例如 last_seen 早于 B_start）→ 'incomplete'
          ⚠️ 必须与「缺勤」区分：可能只是摄像头没拍到，不等于没来上班
```

**`incomplete` 这个状态是必须的**。如果只有「缺勤」一种，
那么「摄像头坏了导致没人被识别」会被整体判成全员缺勤 ——
这在实操中是灾难性的，会让考勤数据完全不可信。

### 3.4 跨天班次

夜班 22:00–06:00 跨天，`work_date` 必须归属到**上班那天**：

```
若 cross_day=1 且 识别时间 < B_end  → 归属到前一天
否则                                → 归属到当天
```

不这样处理，夜班会被拆成两天各半段，考勤全乱。

## 四、风险与边界（必须写进产品说明）

### 4.1 ⚠️ 核心局限：视频考勤可被「代打卡」

```
只要拿着别人的照片站在镜头前，就能通过识别。
```

这是**技术路线固有的**，不是实现缺陷：

- 现有方案是**2D 人脸比对**，没有活体检测（liveness detection）；
- 加活体检测需要额外的红外/深度摄像头或专门的活体模型，
  成本和复杂度都会显著上升，且手机端推流方案无法支持；
- 戴口罩时识别本身就不可靠（见 README「六之五」），
  而工地上戴口罩是常态。

**因此定位必须是**：

> 本功能用于「在岗情况辅助统计」与「安全合规趋势分析」，
> **不可作为工资核算、纪律处分的唯一依据**。
> 若要用于严格考勤，需配合活体检测设备或闸机等硬件。

这条必须在页面上显式提示，不能只写在文档里 —— 否则一旦被当成绩效依据，
纠纷时无法解释。

### 4.2 其它边界

| 风险 | 表现 | 缓解 |
|---|---|---|
| 摄像头视野有限 | 有人从盲区进出 → 漏检 | 报表区分 `incomplete`；支持多摄像头合并 |
| 光照/角度差 | 识别失败 → 记成访客 | 访客数据**不计入考勤**，仅记入合规统计 |
| 同一人多次误识别为不同访客 | 考勤缺失 | 临时编号不参与考勤判定（只认 `person_id`） |
| 长时间盯着镜头 | 被误判为一直在岗 | 无法解决；靠「在岗时长仅供参考」的定位兜底 |
| 数据保留 | 人脸+考勤属个人信息 | 参照《个人信息保护法》：明示告知、最小必要、定期清理 |

### 4.3 只有「已注册人员」参与考勤

**临时访客编号一律不产生考勤记录**。原因：

- 访客编号是按特征指纹临时生成的，重启后会重新发号，
  跨天无法对应到同一个人，拿来算考勤会产生大量幽灵记录；
- 未注册人员本来就无法确认身份，算考勤没有意义。

这条要在代码里硬性保证：`att` 相关查询一律加 `is_temp = 0` 条件。

## 五、分阶段实施计划

### 阶段一：只读报表（不改识别链路，风险最低）

**目标**：把现有的 `face_seen` 用起来，产出「谁今天来过、待了多久」。

- 新建 `webapp/attendance.py`：会话归并 + 日结计算
- 新建 `/attendance` 页面：按日 / 按人查看在岗情况
- 数据来源：直接读 `face_seen`，**不新增采集**
- 不引入班次概念，只展示「首次出现 / 末次出现 / 在岗时长」

**产出**：一个能用的在岗统计页，且完全不触碰已稳定的识别链路。
**验收**：给定构造的 `face_seen` 流水，日结结果与手工计算一致（单元测试覆盖）。

### 阶段二：引入班次与状态判定

- 建 `att_shifts` / `att_daily` 表
- 支持配置班次、绑定人员
- 计算迟到 / 早退 / 缺勤 / 记录不全
- 页面增加「今日考勤看板」与异常列表
- **在页面显著位置标注 4.1 节的定位说明**

**验收**：跨天班次、宽限时间、缺勤判定边界均有单元测试。

### 阶段三：与安全合规联动（本系统的差异化价值）

这一阶段才是**本系统相对通用考勤软件的真正优势**：

- 谁「没戴安全帽」的同时正在岗位上 → 直接对应到人和班次
- 输出「某人当月未戴安全帽 12 次」这类**可落到人头的安全台账**
- 支持导出为安全培训 / 处罚的参考依据（注意 4.1 的定位）

### 阶段四（可选）：对接外部考勤系统

若要接入公司现成的人脸考勤机 / OA 系统：

- 需要对方提供**接口文档**（协议、鉴权方式、字段定义）
- 我方作为数据提供方，推送 `att_daily` 日结数据（不是原始流水）
- ⚠️ 没有接口文档无法开展，不要凭猜测对接

## 六、实现前需要确认的问题

以下问题会直接影响数据模型，**开工前需要明确**：

1. **班次怎么定？** 是所有人统一上下班，还是按岗位分多班次？
   是否需要支持跨天夜班？（影响 `att_shifts` 的复杂度）
2. **中午休息算不算工时？** 影响「会话时长求和」还是「首末相减」。
3. **「记录不全」要不要报警？** 如果摄像头经常拍不到人，
   考勤数据会大面积异常，需要先确认现场摄像头的覆盖质量。
4. **要不要对接外部系统？** 若需要，先拿到接口文档。
5. **数据保留多久？** 人脸特征与考勤记录同属个人信息，
   需明确保留期限与清理策略（建议：原始流水 90 天，日结 2 年）。
